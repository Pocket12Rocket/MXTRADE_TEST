# Tech debt register — Fast Sport / MXTrade

**Date:** 2026-09-19
**Next free IDs:** `PERF-20` · `BUG-12` · `SEC-37` · `DOS-20` · `ARCH-15` · `DX-05` · `LEGAL-30`

This register collects the findings of four read-only audits (Firestore query/caching cost, security & rules, repo structure & architecture, denial-of-service & cost amplification) plus a legal/compliance research pass, run against this repo on 2026-09-19, plus the owner's decisions on how to treat them. It exists so that issues found once don't need to be rediscovered: every row is a discrete, evidence-backed item that any contributor (human or agent) can pick up, fix, and close.

## How to use this register

- **Adding an item:** pick the prefix for the area (see below), use the next free number in that prefix's series (the header's **Next free IDs** line above, or the highest ID currently in that table + 1 if this line is stale), and fill in every column. Evidence must be a real `file:line` (or `file:startLine-endLine`) you have actually looked at — not a guess.
- **Prefixes:** `PERF-` (Firestore reads/writes & caching) · `BUG-` (correctness bugs in query logic) · `SEC-` (security & rules) · `DOS-` (denial-of-service & cost amplification) · `ARCH-` (structure & architecture) · `DX-` (tooling, lint, tests, versions) · `LEGAL-` (legal & compliance, sourced from `docs/LEGAL_COMPLIANCE.md`).
- **Severity:** `Critical` / `High` / `Medium-High` / `Medium` / `Low-Med` / `Low` (the caching design rows, `PERF-00` and `PERF-17`, use `Design` since they aren't defects). Use the same judgement calls the audits used: Critical = data loss, money, or full compromise; High = a real exploit or a correctness bug that loses/corrupts data; Medium = abuse or waste with a workaround or limited blast radius; Low = hygiene, inconsistency, or a paper cut. `Medium-High`/`Low-Med` are half-steps used where a flat Medium/Low under- or overstates it (currently only in the DOS table).
- **Row order:** within each table, rows are sorted **by severity, high to low** (Design rows sit at the very top of PERF as design notes, above Critical); where a table has a **Launch blocker** column, `yes` rows sort before `no` rows at the same severity. **IDs are assigned in discovery order and no longer indicate row position** — always use the ID, never "the Nth row", when referring to an item.
- **Status values:** `Open` (default, not started) · `In progress` (someone is actively working it, including a fix that's genuinely partial) · `Fixed — awaiting commit` (the fix is complete in the working tree but not yet committed by the repo owner — the row stays, with a note, until it's committed) · `Won't fix` (a deliberate decision not to act, with a one-line reason in the row).
- **Closing an item:** once a fix is **committed**, DELETE its row from the table (it's no longer debt) and add one line to the `## Fixed log` at the very end of this file: `ID — title — <short commit hash>`. This is the only place a fixed item's ID persists — the table itself never carries a "fixed" row.
- **Never put secret values here.** Reference `.env.local`, a secret name, or a Secret Manager entry by name only — never paste an API key, password, service-account JSON, signature, or token into this file (or into any commit).
- **IDs are permanent.** Once assigned, an ID is never reused or renumbered — not while its row is still in a table, and not after that row is deleted into the `## Fixed log`. Check both the live tables and the Fixed log before assuming a number is free.

> ## Current state
> **This app is pre-launch and in active testing.** PayFast is **intentionally** running in **SANDBOX mode** (`PAYFAST_SANDBOX="true"` in `apphosting.yaml`) with no real accounts and no real money moving. **The security items below (`SEC-xx`, `DOS-xx`) describe launch blockers, not active incidents.** Nothing in this document implies a breach happened or that customer data or funds are currently at risk. Each `SEC-xx`/`DOS-xx`/`LEGAL-xx` row carries a `Launch blocker` column; everything marked `yes` must be resolved (or explicitly accepted with owner sign-off) before `PAYFAST_SANDBOX` is switched off and real payments start.
>
> **Fix priority (owner-set):** launch blockers always come first, full stop. After that, this project's stated priority is **reducing Firebase/Firestore billing exposure first, application performance second** — everything else (hygiene, structure, legal, DX) follows. The Top 10 list and the Suggested fix order below are both ordered on that basis.

### Top 10 right now

Highest-impact open items across every table, in the owner's stated priority order — launch blockers first, then Firestore/Firebase cost impact, then performance. ("Open" here includes `Fixed — awaiting commit` rows: until something is actually committed and deployed, its cost/risk is still fully live.)

1. **SEC-01** — PayFast ITN validation is skipped by default in sandbox, with no signature/IP/`merchant_id` checks even when it runs (Critical, launch blocker).
2. **SEC-02** — A seller can get any product deleted, and inject fields, through the approval flow (Critical, launch blocker).
3. **SEC-03** — Next.js 15.2.9 carries multiple critical RCE advisories (Critical, launch blocker).
4. **DOS-01** — Unbounded public Firestore reads from any browser tab, ≈$108/hr from one client with no account (Critical, launch blocker, direct billing risk).
5. **DOS-04** — Oversized public images cause origin-hit egress cost *and* can saturate the entire 800-request concurrency ceiling — a billing risk and an outage risk together (High, launch blocker).
6. **DOS-02** — Unfiltered public collection scans (`sellerPublicProfiles`, `faqs`, `siteContent`, `catalogConfig`) cost a full collection read per call, repeatable at will (High, launch blocker).
7. **DOS-03** — Anonymous `clickCount` write amplification, ≈$155/day at scale plus write contention on checkout-critical documents (High, launch blocker).
8. **PERF-00** — The recommended caching design (`catalogMeta/versions` + layers 1-2): the actual long-term fix for the read-cost problem underlying DOS-01/02/18; not yet built (Design).
9. **PERF-01 / PERF-02 / PERF-03 / PERF-04** — The layer-0 query-shape fixes (home page, seller-profile N+1, admin badge polling, pagination): the biggest already-realized Firestore cost win in the repo, but all of it is sitting **uncommitted** — none of the savings are live until it ships.
10. **PERF-05** — `clickCount` write on every product view, anonymous, still `Open`: both a direct cost/write-amplification issue (see DOS-03) and the hard prerequisite blocker for shipping PERF-00 at all.

### Caching layers

The recommended design (PERF-00) sits within a four-layer model the caching audit worked through:

- **Layer 0 — fix query shape (no staleness introduced).** Bound every query, stop N+1 seller/product lookups, batch multi-document writes, replace polling counters with `getCountFromServer`/listeners. This is PERF-01 through PERF-15 above. Do this regardless of anything else.
- **Layer 1 — server-side shared cache (ISR).** `getStaticProps` + `revalidate` (Admin SDK) for home, catalog's first page, `product/[id]` (`fallback:'blocking'`), FAQ, About; trigger `res.revalidate()` on-demand from approve/pricing/notify/cancel/CMS paths. Reads then scale with revalidations, not visitors. Caveat: verify ISR cache/CDN behaviour on Firebase App Hosting across instances before relying on it.
- **Layer 2 — client cache across navigations (TanStack Query / SWR).** One shared in-memory query cache surviving client-side navigation, fed by the single `AuthProvider`. Optional IndexedDB persistence (`persistQueryClient` + `idb-keyval`) with a `maxAge`/build-id buster, but **only for public queries** (`shouldDehydrateQuery` allowlist) — never `users`/`sellerPrivateProfiles`/`orders`/`refundRequests`. Clear the persisted client on logout.
- **Layer 3 — Firestore `persistentLocalCache` + `persistentMultipleTabManager`.** Helps listeners and `getDocFromCache`, but a plain `getDocs` still bills the full result, and it would cache **everything read** — including bank/ID numbers — unencrypted in IndexedDB. Logout requires `terminate()` + `clearIndexedDbPersistence()`, which discards pending writes and fails if other tabs are open. **Recommendation: do not use this layer for this app.** Keep the default in-memory Firestore cache and implement layers 0–2 instead.

### DoS mitigation plan

**Phase 0 (before real traffic):**
1. App Check with reCAPTCHA Enterprise, enforced on Firestore + Storage, verified in every `pages/api` route via `getAppCheck().verifyToken(req.headers['x-firebase-appcheck'])`, monitoring mode first then enforce — closes or blunts DOS-01, DOS-02, DOS-03, DOS-08, DOS-09, DOS-11, and every row whose only existing mitigation is a spoofable rate limit.
2. Recompress `public/images` (54 MB → under 2 MB) + `next.config.js` `headers()` with `Cache-Control: immutable` (DOS-04).
3. Cap the ITN body size + add `rateLimit` to `notify.js` (DOS-07).
