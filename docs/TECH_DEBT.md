# Tech debt register — Fast Sport / MXTrade

**Date:** 2026-09-19

This register collects the findings of three read-only audits (Firestore query/caching cost, security & rules, repo structure & architecture) run against this repo on 2026-09-19, plus the owner's decisions on how to treat them. It exists so that issues found once don't need to be rediscovered: every row is a discrete, evidence-backed item that any contributor (human or agent) can pick up, fix, and close.

## How to use this register

- **Adding an item:** pick the prefix for the area (see below), use the next free number in that prefix's series (e.g. the highest `PERF-xx` in the table + 1), and fill in every column. Evidence must be a real `file:line` (or `file:startLine-endLine`) you have actually looked at — not a guess.
- **Prefixes:** `PERF-` (Firestore reads/writes & caching) · `BUG-` (correctness bugs in query logic) · `SEC-` (security & rules) · `ARCH-` (structure & architecture) · `DX-` (tooling, lint, tests, versions) · `LEGAL-` (legal & compliance, sourced from `docs/LEGAL_COMPLIANCE.md`).
- **Severity:** `Critical` / `High` / `Medium` / `Low` (the caching design row, `PERF-00`, uses `Design` since it isn't a defect). Use the same judgement calls the audits used: Critical = data loss, money, or full compromise; High = a real exploit or a correctness bug that loses/corrupts data; Medium = abuse or waste with a workaround or limited blast radius; Low = hygiene, inconsistency, or a paper cut.
- **Status values:** `Open` (default, not started) · `In progress` (someone is actively working it) · `Fixed (commit)` (done — replace the literal word `commit` with the short commit hash that fixed it) · `Won't fix` (a deliberate decision not to act, with a one-line reason in the row).
- **Closing an item:** change `Status` to `Fixed (<short-hash>)` in the same PR/commit that fixes it, or immediately after. Don't delete rows — the register is a log, not a to-do list that gets tidied away.
- **Never put secret values here.** Reference `.env.local`, a secret name, or a Secret Manager entry by name only — never paste an API key, password, service-account JSON, signature, or token into this file (or into any commit).
- **IDs are permanent.** Once assigned, an ID is never reused or renumbered, even after the row is fixed or marked won't-fix, so old links/PRs stay valid.

> ## Current state
> **This app is pre-launch and in active testing.** PayFast is **intentionally** running in **SANDBOX mode** (`PAYFAST_SANDBOX="true"` in `apphosting.yaml`) with no real accounts and no real money moving. **The security items below (`SEC-xx`) describe launch blockers, not active incidents.** Nothing in this document implies a breach happened or that customer data or funds are currently at risk. Each `SEC-xx` row carries a `Launch blocker` column; everything marked `yes` must be resolved (or explicitly accepted with owner sign-off) before `PAYFAST_SANDBOX` is switched off and real payments start.

### Caching layers

The recommended design (PERF-00) sits within a four-layer model the caching audit worked through:

- **Layer 0 — fix query shape (no staleness introduced).** Bound every query, stop N+1 seller/product lookups, batch multi-document writes, replace polling counters with `getCountFromServer`/listeners. This is PERF-01 through PERF-15 above. Do this regardless of anything else.
- **Layer 1 — server-side shared cache (ISR).** `getStaticProps` + `revalidate` (Admin SDK) for home, catalog's first page, `product/[id]` (`fallback:'blocking'`), FAQ, About; trigger `res.revalidate()` on-demand from approve/pricing/notify/cancel/CMS paths. Reads then scale with revalidations, not visitors. Caveat: verify ISR cache/CDN behaviour on Firebase App Hosting across instances before relying on it.
- **Layer 2 — client cache across navigations (TanStack Query / SWR).** One shared in-memory query cache surviving client-side navigation, fed by the single `AuthProvider`. Optional IndexedDB persistence (`persistQueryClient` + `idb-keyval`) with a `maxAge`/build-id buster, but **only for public queries** (`shouldDehydrateQuery` allowlist) — never `users`/`sellerPrivateProfiles`/`orders`/`refundRequests`. Clear the persisted client on logout.
- **Layer 3 — Firestore `persistentLocalCache` + `persistentMultipleTabManager`.** Helps listeners and `getDocFromCache`, but a plain `getDocs` still bills the full result, and it would cache **everything read** — including bank/ID numbers — unencrypted in IndexedDB. Logout requires `terminate()` + `clearIndexedDbPersistence()`, which discards pending writes and fails if other tabs are open. **Recommendation: do not use this layer for this app.** Keep the default in-memory Firestore cache and implement layers 0–2 instead.
